The rule

A component name describes what the thing is, in words that survive the module it was built for. Four tests, applied in order — a name that fails any one of them is not the name.

1
Name the shape, not the business objectThe library ships RecordCard, RecordForm, RecordDetailModal — never PurchaseRequestCard or LeaveRequestForm. A component that names one object cannot be reused by the next module without a lie in its name. The only family allowed to know the domain is workflow/, and even there the object is the generic one: a record, an approval, an audit entry.
2
Nouns, never verbsA component is a thing on screen, not the action a screen performs with it. ConfirmModal, not SubmitConfirmModal / DiscardConfirmModal / ReviewSubmitModal. If a name needs a verb to be understood, the verb belongs in a prop (variant="discard") or in the consuming screen's own wrapper.
3
No invented role wordsNothing is a Viewer, Manager, Handler, Wrapper, Helper or Kit-of-convenience. Use the plain word for the UI object: Card, Modal, Panel, Form, List, Table, Tag, Stepper, Trail. Two words maximum: <Object><UiNoun>.
4
One name per job — capability goes in propsBefore adding a component, look for the one that already does this job with a flag added. A second component is justified only when the two carry different contracts, not when they carry different settings. Density, search, multi-select, placement and tone are settings.
The merge test

Applied to every pair that looked like a duplicate. If all three answers are yes, they are one component with a variant.

TestWhat it means
Same contract?The same required inputs and the same event vocabulary. Badge and StatusChip both took a label and rendered a tone pill — same contract. FormSection and DetailSection do not: one owns validation and focus order, the other owns copyable values.
Same place in a page?Interchangeable at the call site. Toast and Banner both announce something about the current view — placement is the difference, so placement became the variant.
Would a reader ask which one?If a designer has to be told the rule to pick between two names, the rule should be a prop instead. SearchSelect vs CreatableSelect vs MultiSelect failed this badly — they are capabilities of one picker.

Still separate — and why

Tag · Avatar

Different contracts. A tag carries a label and a tone; an avatar carries a person.

RecordCard · PersonCard

A person is not a record. No status, no lane, no approval footer.

FormSection · DetailSection

Labels, validation and focus order versus copyable values and an edit hand-off.

EmptyState · ErrorState

Expected nothing versus something failed. Different copy, different recovery.

DataTable · EditableTable

Read and select versus inline add / edit / delete inside a form.

FilterPanel · FilterBuilder

Facets versus rules. Both mount inside PageControls; neither replaces the other.

When you add a component

The checklist, in order. Steps 1 and 2 remove most proposed components before they are written.

1
Search the merge table aboveIf the job is already covered by a variant, add the call, not the component.
2
Run the merge test against the nearest neighbourThree yeses mean you are adding a prop to that neighbour instead.
3
Name it with rules 1–4, then write the .d.tsThe declaration is the API. Prop names come from the shared vocabulary — tone, variant, size, selected, loading, error, empty, disabled, busy.
4
Ship the specimen card in the same changeVariants and states, or it isn't done — an undocumented component gets re-invented in the next module.
5
Retire, never deleteA superseded component loses its .d.ts and its card and gains an @internal header pointing at its replacement. Imports keep resolving; the documented surface shrinks.
