1 · Page anatomy

Every desk page is the same five regions in the same order. The shell owns the frame; the page owns only what sits between the title bar and the footer. If a page needs a region that isn't here, that is a signal to reconsider the page, not to add a region.

ShellHeader — brand cell · module tile + breadcrumb · bell · gear · presence · profile
NavRail
drawer ⇄ icon ⇄ overlay
PageTitleBar — icon + title · scope Tabs with counts · view switcher · actions
PageControls — search · filters · date range · sort · columns · primary action · pagination
Content view — list / card / kanban / timeline / calendar
Workspace
Pane
ShellFooter

Two rules this encodes. The title bar owns the view switcher whenever both it and PageControls are on screen — the toolbar only carries the switcher on pages with no title bar. QuickStats sits between them when a page has one, because it is a filter that also summarises.

2 · The five content views

One record set, five renderings, one filter contract. Search, facet filters, date range and the quick-stat filter apply identically to all five — a view swap must never change what the user is looking at, only how.

ViewComponentReach for it when
ListDataTableComparing many records on the same fields. The default, and the only view with a column chooser.
CardRecordCardEach record needs more than a row can hold — people, status and an action together.
KanbanKanbanBoard + RecordCardStatus is the thing being managed, and moving a record between states is the work.
TimelineGanttTimelineDuration and overlap matter — scheduling, load, what runs at once.
CalendarCalendarRecords are keyed to a date and the question is "what falls on this day".

Every one of them takes the same loading · empty · error props, in the same precedence: error → loading → empty → content. A failed fetch must never read as an empty region.

4 · Record-detail page

Opening one record — a person, an asset, a request. Two columns: identity on the left, the record's own sections on the right. Only the field lists change between modules.

Identity — Avatar · name · role · Rating
DetailList — key/value rows, copyable IDs in the data face
Header — back · title · Tag · DropdownMenu actions
Tabs — the record's own sections
StatCard strip — the two or three figures that matter
DetailSection ×N — grouped fields, each with its own edit hand-off
AttachmentRow ×N — inside a DetailSection

The page is read-only by default. Editing is a hand-off, not a mode: a section's pencil opens the form that owns those fields (RecordForm mode="edit" or a scoped Panel). That keeps one component responsible for validating any given field.

Using these

A new module starts from the Desk App Scaffold template, which is these four patterns already assembled — swap data.js and the labels. Build a page by hand only when it genuinely doesn't fit one of them, and when that happens, say which region is wrong before adding a component.
