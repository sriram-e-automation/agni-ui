Versioning & change SOP

How a change to AgniUI becomes a version other people can rely on. The full procedure is in CONTRIBUTING.md; this card is the part you need at the moment you are editing a component.

A change that is not written down is a change that breaks someone quietly.

Two levels of version, and what each answers

LevelLives inAnswers
Package versionpackage.json · CHANGELOG.md"What am I installing?" One number for the whole library — @agnikul/agniui@1.0.0.
Component version@version in each <Name>.d.ts"Has this component's contract changed since I last read its card?" — without diffing a whole release.

Bump rules — identical at both levels

BumpThe change
majorA prop removed or renamed · a default changed · a component renamed or retired · a token deleted. A changed default is a major even though nothing was removed: every consumer who did not pass that prop gets new behaviour.
minorA prop added · a variant, state or component added · a token added.
patchA visual fix inside the existing contract · docs · a Tailwind class swap with no visual delta. A visual change with no API change is still an entry — "nothing changed in the props" is exactly the release that surprises people.

A component major forces at least a package minor. Two or more component majors in one release make it a package major.

The changeset — one file per change

Written for the person consuming the change, not the person who made it. Name the component, say what moved, say what they have to do.

--- .changeset/pagecontrols-export.md ---
---
"@agnikul/agniui": minor
---

PageControls: added `exportAction`, `primaryAction` and `secondaryActions`.
`exportAction.enabled: false` renders the export button visible and disabled
with a reason rather than hiding it — a records page should not change shape
per viewer. The `actions` ReactNode slot still works and renders after the
declarative group.

If any component took a major, add the migration line in as many words as it takes:

Migration: pass `actions={<Button iconOnly icon={…} />}` to keep the ⋮ button.

The review gate — four checks, in this order

  1. .d.ts matches .tsx. The .d.ts is the published contract; if they disagree, the .d.ts is wrong.
  2. The card shows the new state. Not "the code supports it" — the card shows it.
  3. The changeset says what a consumer must do, and the bump level matches the table above.
  4. readme.md names the component. A component absent from the index does not exist as far as the next person is concerned.

Releasing

npx changeset version   # folds .changeset/*.md into CHANGELOG.md, bumps package.json
npx changeset publish   # builds, publishes, tags

In practice CI does both: merge a PR carrying its changeset, the bot opens a "Version Packages" PR, and merging that one publishes. Nobody runs npm publish by hand, so the changelog cannot drift from what shipped. Never hand-edit a released section of CHANGELOG.md — correct it with a new patch entry.

Retiring a component — three releases, never a delete

1 · Deprecate minor

Add @deprecated Use <X> instead. to the .d.ts. It still works, still has a card, and the card gains a banner naming the replacement.

2 · Withdraw major

Remove the .d.ts and the specimen card. The .tsx stays with an @internal header naming the replacement, so imports inside the library keep resolving. This is what the Aug 2026 merge did to sixteen components.

3 · Delete

Only when nothing in the repo imports it. Usually never — a dead .tsx costs nothing and keeps history readable.

The merge test comes first

Before any of this: does the thing you are adding differ in shape, or only in capability? Capability goes in props. See component-naming.card.html.
